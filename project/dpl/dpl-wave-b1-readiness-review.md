**Review date:** 2026-10-20  
**Decision:** **PASS — HOLD DPL-12; AUTHORISE B2 ONLY**

## Question

> **Do the four B1 contracts compose into one executable direction, what concrete evidence is still missing, and what is the smallest next wave that advances real deployment without freezing prose abstractions into software too early?**

The answer is:

> **Yes, B1 composes cleanly. No, shared deployment orchestration is not yet ready to freeze. One further four-lane vertical-slice wave is warranted before DPL-12.**

B1 has moved DPL from abstract ontology into controlled external-authority and site-interface contracts, but it still lacks the four things most likely to expose a premature shared implementation:

1. one **real site manifest** produced from messy public evidence;
2. one **substantive England technical obligation family** below the legal/source spine;
3. one **substantive London strategic planning obligation family** below the source/status spine;
4. one **site-interface response family** below the package-authority register.

DPL-12 should consume those objects rather than invent their common structure in advance.

# 2. Cross-object composition test

B1 passes the authority-composition test.

Consider a future real candidate with:

- uncertain legal parcel geometry;
- an apparent front-to-rear fall;
- a mature tree close enough to make ground/foundation assumptions material;
- unknown below-ground services;
- a known London borough;
- a qualifying Building Regulations application date not yet reached;
- an operative strategic/local planning composition still being assembled.

The four B1 contracts assign those questions without overlap:

```text
REAL-WORLD EVIDENCE
      ↓
DPL-14 / DPL-06
site claims + UNKNOWNs + provenance
      │
      ├──────────────→ DPL-08A
      │                package duties / architectural interface response
      │
      ├──────────────→ DPL-09A
      │                exact England source/applicability selection
      │
      └──────────────→ DPL-10A
                       exact planning source/membership/status selection
```

None of those layers owns the conclusion of another.

A visible mature tree does not become a foundation design.

A building-control application date does not become a planning source.

A borough identity does not become a planning-permission result.

A site-interface package does not declare the statutory requirement it must satisfy.

That separation is the main B1 success.

# 3. Shared claim flow

```text

      ↓
SITE / PROJECT CLAIM
      ↓
SOURCE / TARGET APPLICABILITY
      ↓
OBLIGATION
      ↓
SITE-INTERFACE OR OTHER RESPONSE
      ↓

      ↓
DPL-03 RESULT
```

The flow is intentionally not:

```text

```

or:

```text

```

or:

```text

```

B1 therefore preserves the original DPL proposition: the compiler evaluates admitted representations and exposes obligations; it does not silently author architecture or impersonate external decision-makers.

# 5. DPL-12 readiness — HOLD

## Decision

**Do not start DPL-12 after B1.**

This is not because the foundation is weak. It is because it is now strong enough to expose what is still missing.

Starting DPL-12 today would require the implementation to invent, from prose:

- the first stable real-site claim encoding;
- the source/applicability object fields actually needed by one technical family;
- the planning obligation/source fields actually needed by one strategic policy family;
- the response/option representation needed by one site-interface package.

That would reverse the intended dependency:

```text
BAD
shared schema
   ↓
force each domain to fit it
```

Instead B2 should produce:

```text
real site record
technical obligation family
planning obligation family
interface response family
        ↓
compare actual common seams
        ↓
DPL-12 minimal substrate
```

DPL-12 should then be smaller and more trustworthy.

## What B2 must earn for DPL-12 re-entry

At the next integration gate, require at minimum:

1. three real screening manifests that survive heterogeneous public sources;
2. one England technical family with exact sources, applicability, admitted methods and unresolved external evidence;
3. one London strategic policy family with exact source status and deterministic/evidence/judgement splits;
4. one site-interface family represented as conditional response obligations/options without construction pseudo-precision;
5. a demonstrated common identity/provenance seam across those four objects.

Only then should DPL-12 freeze shared orchestration types.

# 6. Empirical readiness — DPL-14B authorised

## Decision

Authorise **DPL-14B — three-site real-corpus pilot**.

Do not jump directly to all 24 plots.

The pilot is no longer a disposable dry run. The three records must use the final DPL-14A admission protocol and may count toward the eventual corpus if they survive review.

## Pilot design

Choose three materially different Greater-London plots, preferably in **three different boroughs**, so the first pilot cannot accidentally become a first-borough cohort.

The three should differ materially on several of:

- apparent width/depth relation;
- access morphology;
- orientation;
- plot shape;
- neighbour/edge condition;
- topography;
- tree/landscape condition;
- heritage/environmental trigger;
- source quality.

At least one should be an intentional challenge case rather than an easy apparent fit.

## Required outputs

DPL-14B should produce:

- three admitted/rejected candidate decisions under the frozen protocol;
- three screening manifests for admitted pilot sites;
- claim-level provenance/precision/unknowns;
- one minimal machine-readable representation **only if the three records demonstrate a stable common shape**;
- protocol defects/field additions where real evidence exposes them;
- no compatibility/deployment verdict.

## Borough consequence

Do not select DPL-10C's first borough from a three-borough pilot.

The first borough remains an empirical outcome of the expanding corpus and should meet DPL-14A's varied mini-cohort rule.

# 7. Site-interface readiness — DPL-08B authorised

## Decision

Authorise one first substantive site-interface vertical slice:

> **DPL-08B — ground, datum, plinth and accessible-approach interface.**

This packet is chosen because it is simultaneously:

- architecturally important;
- strongly site-dependent;
- already represented by Reference House plinth/perimeter/entrance duties;
- exposed by DPL-RS-01's modest fall and approach assumptions;
- likely to be attacked immediately by real plot topography;
- connected to England structure/moisture/access obligations without belonging to those external authorities.

## Scope boundary

DPL-08B may author:

- building-side interface requirements;
- conditional response classes;
- datum/finished-ground relationships;
- accessible-approach handoff logic;
- perimeter dry-zone/plinth duties;
- evidence inputs and failure/rewind conditions.

It may **not** manufacture:

- foundation sizes/reinforcement;
- geotechnical capacity;
- retaining-wall engineering;
- drainage engineering;
- an exact real-site grading design without site evidence;
- a construction detail merely to give DRW something to draw.

If a site response crosses DPL-02 protected order, DPL-08B must surface the conflict rather than solve it by geometry drift.

## Relationship to DPL-14B

08B and 14B may proceed laterally.

08B should use DPL-RS-01 as its canonical synthetic fixture and then be replayed against the three 14B pilot sites at the B2 integration gate.

No requirement that 08B wait for all three real sites is imposed.

# 8. England technical readiness — one first domain only

## Decision

Authorise **DPL-09B — structure, ground, moisture and materials target family**, with a mandatory packet split if authority recovery proves the combined domain too large for one restart-safe issue.

Do not open DPL-09C–I yet.

## Why this family first

This is the technical family most tightly coupled to land deployment:

- Part A / structural support;
- Part C / site preparation and resistance to contaminants/moisture where applicable;
- Part D where applicable;
- Regulation 7 / materials and workmanship;
- geotechnical/site evidence;
- professional structural/material evidence.

It can directly test the core DPL principle that:

> an applicable requirement the compiler cannot natively prove remains visible and unresolved.

The likely result is not a giant native structural solver.

A good DPL-09B result may instead separate:

```text
machine-checkable applicability / geometry
        +
controlled site inputs
        +
external structural / geotechnical evidence
        +
explicit unsupported domains
```

## Split rule

Before substantive encoding, recover the exact legal/guidance/evidence authority.

If structure/geotechnics and moisture/materials produce materially independent method/evidence systems, split 09B into restart-safe subpackets rather than forcing them through one PR.

The B1 gate authorises the **family**, not a monolithic implementation.

```text

REGULATORY TECHNICAL     DPL-09B
STRATEGIC PLANNING       DPL-10B
EMPIRICAL REAL SITES     DPL-14B
```

They can proceed substantially in parallel.

Their integration point is stronger than any pairwise dependency:

```text

                    │

                    │
              14B real sites
                    ↓
              B2 INTEGRATION
                    ↓
          DPL-12 readiness decision
```

The next gate should test the same three real sites against the first technical/planning/interface families before common software types are frozen.

# 11. Rejected next-wave alternatives

## Start DPL-12 now — rejected

Would freeze shared structures from contracts rather than from multiple concrete domain objects.

## Collect all 24 real plots now — rejected

Would multiply site records before the first three prove the field/provenance shape.

## Pick a borough now — rejected

Would violate DPL-14A's empirical selection rule and risk overfitting the local-planning plug-in to familiarity or convenience.

## Open every DPL-09 technical child — rejected

Would turn the regulatory inventory into a large parallel implementation programme before one technical family has proved the source/evidence/method pattern.

## Open every DPL-10 planning child — rejected

Would encode local/evidence/judgement interfaces before strategic and empirical seams are proven.

## Run DPL-08B only after all real sites exist — rejected

Would unnecessarily serialize a synthetic-reference-site interface problem that can be authored conditionally and later attacked by real sites.

## Promote DPL to M3 — rejected

The work is developed and coherent, but there is still no coordinated deployment case or demonstrated deployment compiler substrate.

# 12. DRW rendezvous refresh

At the review baseline, DRW has entered DRW-11 bounded-detail work.

Relevant recent behaviour reinforces rather than challenges the DPL boundary:

- DRW-11A froze a bounded detail register;
- DRW-11B refused an unearned permanent-opening construction detail rather than invent technical authority;
- DRW-11C records the service-riser detail as not required where existing spatial/maintenance drawings already carry the authorised information and unresolved technical closures remain outside drawing authority.

The concurrency rule therefore remains:

> **DRW may represent controlled architectural authority; it may not invent site/ground-interface or technical construction authority ahead of DPL/specialist evidence. DPL may create duties and interface authority; it may not mutate controlled house geometry through drawing code.**

### B2-specific hold

Until DPL-08B closes, DRW should not author a construction-complete detail for:

- ground-to-plinth relationship;
- accessible entrance approach/threshold as a site solution;
- foundation/ground interface;
- retaining condition;
- external site drainage connection.

Analytical or clearly unresolved representation remains permissible where already authorised.

DPL-08B itself does not demand that DRW pause.

# 13. Merge-race audit from DPL-14A

DPL-14A exposed one process edge case during this review.

Its PR head was fully validated against `main` `60316f54f8323c0d88c6321e2908da7adc83685f`.

DRW-11C then landed in the narrow interval between the final base check and the GitHub merge transaction. DPL-14A therefore merged with actual first parent:

`3364715144f8e03ac2a65215bd99c03b280887ca`

rather than the last checked base.

The intervening delta was one disjoint DRW file only:

`docs/publication/architectural-drawing-drw11c-service-riser-detail-decision.md`

There was no DPL path overlap or semantic authority conflict.

This review branch starts from the combined DPL-14A + DRW-11C main tree (`7dab53697a556715dff64a01cf640b5f140fc8e9`). Full green validation of this review therefore serves as the immediate integrated-tree proof missing from the race window.

Operational lesson:

- continue final base checks;
- recognise that the current merge API guards expected **head** but not expected **base**;
- where a race still occurs, inspect first parent/delta explicitly and immediately validate the integrated combined state before further dependent work.

Do not describe such a race as a clean exact lease.
