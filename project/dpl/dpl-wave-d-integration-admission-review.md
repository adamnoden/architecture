# DPL-D — Post-Wave-D Integration and DPL-13 Admission Review

**Disposition:** **PASS — ADMIT DPL-13A ONLY; KEEP WHOLE-SITE CONCLUSIONS UNAUTHORISED; HOLD DPL-13B+ AND DPL-15+**

## 1. Decision

Wave D is coherent enough to justify the first canonical Reference House × Reference Site compile.

It is **not** coherent enough to justify a whole-site deployment conclusion.

The distinction is material:

> **A canonical compile may now assemble and evaluate the controlled case without yet claiming that the represented obligation set is complete enough to derive `COMPATIBLE`, `UNRESOLVED` or `INCOMPATIBLE` as an authoritative whole-site result.**

Therefore DPL-13 is admitted only as a first bounded child:

> **DPL-13A — canonical Reference Site case assembly and deterministic deployment ledger.**

DPL-13A must prove one exact synthetic deployment case end to end:

- controlled Reference House identity;
- the authored DPL-RS-01 Reference Site manifest;
- the already-authored rigid 180° Reference Site placement / current unmirrored house as the deployment candidate;
- bounded DPL-02 conformance from DPL-12B;
- DPL-08B + DPL-08C interface identities;
- DPL-09B + DPL-09C England technical targets;
- London strategic planning target;
- explicit Reference Site known / assumed / unknown claims;
- explicit coverage gaps for DPL-11 and other not-yet-runtime-represented due families;
- deterministic case/result identity and invalidation.

It must **not** emit a whole-site deployment conclusion.

DPL-13B is held until 13A demonstrates the exact coverage problem on the canonical case. The likely later question is profile due-obligation coverage / conclusion readiness, but DPL-D deliberately refuses to speculatively design that packet before the canonical case exposes the real seams.

DPL remains **M3 — Coordinated**.

## 2. Why Wave D passes as one system

DPL-C withheld DPL-13 for three specific reasons rather than general caution:

1. no explicit authored candidate / executable Reference House conformance;
2. no proof that the first borough plug-in survived a materially different local source ecology;
3. Wave-C interface / drainage / borough / expanded-corpus objects were not yet composed through the runtime.

Wave D closes each of those gaps without broadening authority opportunistically.

### DPL-12B — candidate and conformance

DPL-12B gives the deployment runtime an explicit authored candidate identity tied to an exact controlled Reference House source fingerprint.

It evaluates only conformance clauses for which executable authority exists, including bounded gross morphology, courtyard, stair and front-field propositions. It preserves unsupported/open DPL-02 clauses as `OPEN` rather than turning prose into fake booleans.

It also retains only the two already-authorised discrete deployment variants:

- `RH-V01` — coherent whole-house mirror;
- `RH-V02` — rigid site placement / cardinal orientation.

A failed candidate remains a candidate-level finding.

No candidate generator, optimiser or route-exhaustion engine was introduced.

### DPL-10D — borough anti-overfit

DPL-10D attacks the Croydon model with Bromley and materially narrows the reusable abstraction.

The result is deliberately small:

- source/status identity;
- development-plan membership;
- method class;
- source provenance/effective state;
- typed obligations;
- proposal-specific external evidence kept external;
- no locality/list-order precedence.

Croydon and Bromley do **not** justify a common local-policy ontology.

Bromley Policy 30 also proves an important negative case: a machine-readable local numeric table must remain unsupported where later strategic policy creates an unresolved temporal/conflict question. Numeric form does not itself earn native authority.

### DPL-12C — runtime composition

DPL-12C then proves the actual Wave-C objects can participate in the same deterministic runtime:

- current eight-site Corpus 1 identity;
- DPL-08C water-interface identity;
- DPL-09C drainage/waste-water target;
- Croydon or Bromley through the narrow borough envelope;
- DPL-12B authored candidate/conformance.

It deliberately does not widen the DPL-12A core loader into a universal parser.

It also discovers an important real limitation: the current eight-site index preserves site identity/challenge metadata but no longer exposes the pilot index's claim-level unknown register. DPL-12C therefore refuses to mine prose into machine facts.

That is exactly the kind of boundary a coordinated deployment system should expose.

### System conclusion

The three Wave-D packets therefore agree on one architecture:

```text
AUTHORED ARCHITECTURE
        ↓
EXPLICIT CANDIDATE
        ↓
BOUNDED RH CONFORMANCE

SITE / SYNTHETIC SITE CLAIMS
        ↓
SITE-INTERFACE IDENTITIES

EXTERNAL NORMATIVE SOURCES
        ↓
TYPED TARGET OBLIGATIONS

EVIDENCE / JUDGEMENT / EXTERNAL DETERMINATION
        ↓
OBLIGATION LEDGER
```

No layer silently acquires another layer's authority.

Wave D therefore passes the M3 coordination test strongly enough to proceed to a canonical integration specimen.

## 3. Original DPL-13 dependency replay

The programme originally placed DPL-13 after:

`DPL-07 / DPL-08 / DPL-09 / DPL-10 / DPL-11 / DPL-12`.

That dependency logic remains correct, but the present state of those workstreams differs materially.

| Dependency | Current state for DPL-13A |
|---|---|
| DPL-07 Reference Site | **concrete enough** — DPL-RS-01 has explicit geometry, placement, assumptions, unknowns and a claim register |
| DPL-08 site interface | **concrete enough for bounded compile** — ground/datum/plinth/access and foul/surface/site-water seams exist; many later interfaces remain outside current runtime |
| DPL-09 England target | **concrete enough for bounded compile** — two controlled technical slices exist; not full Building Regulations coverage |
| DPL-10 London planning | **concrete enough for bounded compile** — London strategic target exists; no local borough is applicable to synthetic DPL-RS-01 |
| DPL-11 non-planning due diligence | **semantically defined but not comprehensively executable** — must be represented as explicit coverage debt / external families, not silently omitted |
| DPL-12 compiler | **concrete enough** — case identity, mixed targets, evidence, candidate/conformance and Wave-C composition are executable |

This is sufficient for one canonical **integration compile** because the point of DPL-13A is to expose how these authorities compose on the controlled synthetic fixture.

It is insufficient for a whole-site conclusion because several dependency families remain incomplete as a due-obligation set.

## 4. Reference Site readiness

DPL-RS-01 is ready to become a machine-readable canonical deployment fixture.

This does not require pretending it is real.

The Reference Site already distinguishes:

- `SYNTHETIC_REFERENCE` site kind;
- authored synthetic assumptions;
- deterministic derived site claims;
- explicit unknowns;
- local coordinate frame and datum;
- exact parcel geometry;
- exact Reference House placement transform;
- approximate neighbour masses where intentionally authored;
- unknown neighbour openings;
- assumed street-network presence of foul sewer / utilities without asserting exact routes/capacity/rights;
- unknown ground, drainage, title-detail, flood, noise, ecology and construction-detail conditions.

Its claim register is therefore materially stronger than the real-corpus index for canonical compiler use.

### DPL-13A rule

DPL-13A may encode only the claims already frozen by DPL-07.

It must preserve at least:

- claim id;
- proposition/value;
- basis (`ASSUMED`, `DERIVED_SITE_CLAIM`, `UNKNOWN`, etc.);
- synthetic site kind;
- relevant dependency/provenance identity.

It must not convert:

```text
ASSUMED
```

into:

```text
MEASURED / AUTHORITATIVE_RECORD
```

merely because the fixture is canonical.

Likewise, an explicit `UNKNOWN` remains an unknown even where a convenient default value would make the compile easier.

## 5. Canonical candidate readiness

DPL-RS-01 already authors the canonical house placement:

- current unmirrored Reference House;
- rigid 180° rotation;
- site-space bounding box X 3.0–15.0 m / Y 14.0–24.8 m;
- model front/south → geographic north / street;
- model technical/east flank → geographic west service side.

This is not compiler-authored adaptation.

DPL-02 explicitly licences rigid translation / rotation under `RH-V02`.

DPL-13A may therefore encode one authored candidate whose provenance points to:

- DPL-07's Reference Site placement decision;
- exact current Reference House revision/source identity;
- `RH-V02` as the admitted conformance-preserving variant route used.

The compiler must not choose the transform itself.

The mirror variant `RH-V01` remains available in the abstract but is **not** part of the canonical Reference Site candidate unless a later authored candidate explicitly invokes it.

## 6. Assurance profile: `SCREENING` is the right first horizon

DPL-13A should compile under:

`SCREENING`

because DPL-RS-01 deliberately contains many unknown conditions that belong later unless accelerated.

This is also the only sensible first canonical profile because DPL-04's purpose for `SCREENING` is precisely to test whether current desktop / fixture evidence supports keeping a site in consideration without pretending to possess feasibility or technical-design evidence.

However, choosing the profile does not establish that the runtime knows the complete `SCREENING` due-now set.

That distinction is the central DPL-D finding.

---

## 7. Why even top-level `UNRESOLVED @ SCREENING` remains unauthorised in DPL-13A

DPL-03 says `UNRESOLVED` is the correct deployment conclusion whenever positive compatibility has not been earned and incompatibility has not been proved.

It would therefore be tempting to say:

> the canonical case obviously contains unknowns, so the compiler may safely emit `UNRESOLVED @ SCREENING` now.

DPL-D rejects that shortcut **at runtime-authority level**.

### The problem is not conservatism; it is scope completeness

DPL-03 defines a deployment conclusion as a **derived conclusion over scoped obligations, evidence and admissible resolution routes**.

The current runtime cannot yet prove that its represented set is the complete set of obligations due for `SCREENING`.

In particular:

- DPL-04 defines due-now categories conceptually but they are not represented as a complete executable profile contract;
- DPL-11 defines major private-law/infrastructure/ground/access/utility families but the runtime does not currently enumerate their complete canonical due set;
- DPL-12B evaluates only a bounded subset of DPL-02 conformance clauses;
- some Reference Site unknowns have not yet been connected to explicit due obligations;
- target coverage is intentionally partial;
- route exhaustion is absent.

A runtime that emits an official `UNRESOLVED @ SCREENING` result from an incomplete obligation universe risks implying:

> **the deployment conclusion machinery has evaluated the whole screening scope and found unresolved items.**

That proposition has not yet been earned.

### What DPL-13A may say instead

The canonical compile may state, explicitly and mechanically:

```text
wholeSiteCompatibilityConclusion: NOT_IMPLEMENTED
conclusionReadiness: NOT_ESTABLISHED
coverageCompleteness: NOT_ESTABLISHED
```

or an equivalent non-conclusion representation.

It may also enumerate the unresolved/unsupported/open findings that it actually represents.

In prose, a reviewer may accurately observe that the case remains unresolved overall.

But the runtime must not promote that observation into the canonical DPL-03 top-level conclusion object until conclusion coverage is itself represented.

This restraint is stronger and cleaner than adding a seemingly conservative status prematurely.

## 8. `COMPATIBLE @ SCREENING` remains forbidden

A positive screening conclusion requires, at minimum, all due-now blocking obligations to be represented and resolved.

The current system cannot establish that.

Exact blockers include:

### 8.1 Due-now obligation completeness

DPL-04's conceptual screening categories are not yet an executable complete due contract.

### 8.2 DPL-02 conformance coverage

DPL-12B proves a bounded subset of conformance clauses. Many identity/protected/interface propositions remain `OPEN` / external.

A candidate cannot be declared wholly within the Reference House contract merely because the implemented subset is green.

### 8.3 DPL-11 coverage

Title/private rights, boundary authority, access rights, sewer/utility rights/capacity, ground and other due-diligence families are not comprehensively represented as current compile obligations.

Some may legitimately be future-due at screening; others may be due if accelerated. The runtime does not yet prove the complete classification.

### 8.4 Site-claim ↔ obligation coverage

DPL-RS-01 has a good claim register, but not every consequential unknown is currently connected to a profile-aware obligation.

### 8.5 Partial target corpus

The England target remains intentionally bounded. A green represented subset cannot become Building Regulations or general deployment compatibility.

Therefore:

`COMPATIBLE @ SCREENING = NOT AUTHORISED`

---

## 9. `INCOMPATIBLE` remains forbidden

Wave D has improved candidate identity but has not earned route exhaustion.

DPL-03 permits incompatibility only after a blocking conflict is shown invariant across relevant conformance-preserving routes, or the relevant routes are exhausted.

Current missing authority includes:

- complete mapping of which route(s) are relevant to each blocking failure;
- evaluation of `RH-V01` where relevant;
- bounded site-interface route exhaustion;
- proof that no conformance-preserving site-interface solution remains;
- invariant-blocker proof machinery.

Therefore:

`INCOMPATIBLE = NOT AUTHORISED`

A DPL-13A candidate may fail an obligation or conformance clause. That remains a candidate/case finding, not a site-level incompatibility conclusion.

## 10. Planning target composition for the synthetic Reference Site

DPL-RS-01 is deliberately a London-context synthetic fixture.

It is **not assigned to a real London borough**.

Therefore DPL-13A must compose:

- London strategic planning authority;

and must **not** fabricate:

- Croydon local policy;
- Bromley local policy;
- any other borough target.

The absence of a local target is not evidence that no local policy would exist on a real site.

It is an explicit limitation of the synthetic canonical fixture.

DPL-13A should expose that limitation as coverage context rather than selecting a borough for convenience.

This is also why DPL-10D remains valuable even though its Bromley target is not part of the canonical Reference Site compile: it has already prevented the runtime from assuming that one local target can stand in for London generally.

---

## 11. DPL-11 integration

DPL-11 is sufficiently mature semantically to inform DPL-13A, but not sufficiently executable to pretend the canonical compile has complete private/non-planning coverage.

DPL-13A should therefore include an explicit **coverage manifest** or equivalent controlled record distinguishing at least:

1. families represented as actual current obligations;
2. families represented only as explicit Reference Site claims/unknowns;
3. DPL-11 families known to be relevant to deployment but not yet executable in the current compile;
4. families legitimately future-due at the requested profile where DPL-04 authority supports that classification;
5. families whose due-now/future-due status itself remains not yet established.

This is not a confidence score.

Its purpose is to prevent a sparse obligation ledger from masquerading as exhaustive coverage.

The coverage manifest itself must be fingerprinted into canonical compile identity if changing it changes the claimed scope.

## 12. Exact DPL-13 decomposition

### Authorise now: DPL-13A

**DPL-13A — canonical Reference Site case assembly and deterministic deployment ledger**

Required responsibilities:

- create a machine-readable DPL-RS-01 manifest from DPL-07 authority;
- preserve synthetic claim basis and explicit unknowns;
- create one explicit authored canonical candidate using DPL-07 placement + `RH-V02`;
- compose DPL-08B/C interface identities;
- compose DPL-09B/C England targets;
- compose London strategic planning target only;
- preserve DPL-12B candidate/conformance findings;
- represent a controlled coverage manifest for DPL-04/DPL-11/partial-target gaps;
- produce deterministic canonical case + ledger identity;
- prove relevant invalidation;
- retain `wholeSiteCompatibilityConclusion = NOT_IMPLEMENTED`;
- retain route exhaustion as not implemented;
- retain candidate generation/selection as not implemented.

### Hold: DPL-13B

A likely future packet will concern:

- executable assurance-profile due-now coverage;
- conclusion-readiness rules;
- possibly conservative top-level `UNRESOLVED` derivation.

But its exact scope must be earned by 13A's canonical result rather than predesigned now.

DPL-13A may discover that the next missing seam belongs instead to DPL-11, DPL-02 conformance coverage, target inventory or another owner.

### Hold: DPL-13C / positive or negative whole-site conclusion machinery

No packet for `COMPATIBLE` or `INCOMPATIBLE` is authorised.

Their prerequisites are materially stronger and should be opened only when the canonical case demonstrates that they are tractable and correctly scoped.

## 13. Maturity decision

DPL remains:

> **M3 — Coordinated**

Wave D makes the workstream much more convincing at M3, but does not earn M4.

M4 means the proposition is **internally validated / controlled** at its stated scope.

The DPL proposition is ultimately deployment machinery capable of evaluating an exact case honestly. The project has now tested important constituent seams, but has not yet produced and adversarially challenged the canonical integrated deployment specimen.

DPL-13A is precisely the next experiment required before M4 can even be reconsidered.

No maturity downgrade is warranted: the workstream remains internally coherent and reconciled with adjacent architecture, site, target and compiler authorities.

## 15. Gate closeout

**DPL-D PASS.**

The programme has crossed an important threshold:

- the first canonical deployment compile is now justified;
- the first canonical deployment **conclusion** is not.

That asymmetry is intentional.

The next correct question is no longer:

> *Do we have enough machinery to assemble the canonical case?*

It is:

> **What does the canonical case expose when every represented fact, unknown, authority and coverage gap is forced into one deterministic ledger?**

DPL-13A owns that question.
