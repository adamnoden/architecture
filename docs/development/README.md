# Development

`docs/development/` contains **internal integration, programme-control and retained execution records** used to move architectural propositions toward coordinated publication, testing or delivery.

This is a provenance/work-control area, not a second source of public architectural truth and not the canonical answer to current project status.

Typical material includes integration and migration programmes, coordination registers and handoffs, adversarial audits and closeouts, prototype/manufacturing planning, and working architectural studies whose results are intended to settle elsewhere.

Concrete build packs, test drawings, protocols and recorded physical results belong in [`../prototypes/`](../prototypes/). Mature appointed-team requirements belong in [`../delivery/`](../delivery/). Public architectural conclusions belong in their owning manuscript, pattern, grammar or Reference House records.

## How to read development records

A development document may accurately describe the state, sequencing or “next” action **at the moment it was written**. That historical statement does not remain current merely because the file is retained.

For present-tense questions use:

1. [`../../STATUS.md`](../../STATUS.md) for project-wide state;
2. the latest explicit owning gate/result for the workstream;
3. older plans, reviews and closeouts for provenance.

When development work settles a durable conclusion, propagate it into the layer that owns that conclusion and leave only the necessary reasoning/history here.

## Authority boundary

Development records may explain **how** a decision was reached. They do not automatically own the resulting architectural claim, executable rule, delivery requirement or present status.

Do not revive a closed programme as a parallel authority merely because its historical control documents are detailed. New evidence should reopen the layer that owns the affected proposition.
