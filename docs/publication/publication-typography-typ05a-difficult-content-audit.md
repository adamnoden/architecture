## 1. Purpose

TYP-05A asks what the book actually needs before inventing a technical typography system.

The repository contains a compiler, TypeScript, tests, machine identifiers and substantial technical work. That does **not** mean the reader-facing book needs to look like software documentation. The audit therefore starts from the Working Edition publication manifest and its print adapters, not from repository file types.

The governing question is:

> **Which reader-facing conditions genuinely stress the frozen TYP-03/04 system enough to earn a new typographic role?**

## 4. Tables are the strongest current stress

The two tables should not be treated as one problem merely because both use Markdown table syntax.

### Compact analytical matrix — Part V

`Part V — Making and Testing the Platform` contains the B0–B3 proportionality table:

- **4 columns**;
- **5 reader rows** including the header;
- longest cell in the current source: **107 characters**.

This is a conventional compact analytical table. It should remain recognisably part of the book rather than becoming spreadsheet graphics.

### Dense implementation schedule — Appendix C

`Appendix C — Reference House Implementation Schedule` contains:

- **5 columns**;
- **41 reader rows** including the header;
- longest cell: **374 characters**;
- most of the corpus's caught unit occurrences.

This is not simply a larger version of the Part V table. It is a long prose schedule whose cells carry complete architectural obligations, owners and reopen conditions. Compressing it into the same small-sans grid risks creating a miniature report inside the book.

### Failure in the current Working Edition default

The working `publication/theme.css` currently applies one table treatment to both cases:

- sans-serif;
- **8.2 pt / 1.32**;
- full width;
- horizontal rules at every row;
- no hyphenation.

That treatment was a sensible working default. TYP-05 must not freeze it by inertia. The Appendix C schedule especially must earn either a genuinely readable table treatment or a more appropriate schedule presentation while preserving its semantic content.

TYP-05B should therefore prove the compact table and the dense schedule **together**, but it may allow them to resolve differently if the content structure earns the distinction.

## 5. Mono is not presently earned

This is the most important negative result of TYP-05A.

### Fenced material

The two fenced blocks are both declared `text` and are architectural sequence diagrams:

1. the external-maintenance route in the Part II composite;
2. the service-topology generative sequence in Part III.

Both use words, spacing and downward arrows to express ordered spatial logic. Neither is code, command syntax, data, a compiler diagnostic or text whose character-cell alignment has independent semantic meaning.

### Inline-code spans

All eight inspected inline-code occurrences are canonical pattern names placed in backticks, for example:

- `High-Service-Room Service Wall`;
- `Visible Leakage Path`;
- `Failure-Tolerant Wet Service Room`;
- `Designed Structural Penetration`;
- `Controlled Attachment Plane`;
- `Coherent Horizontal Service Route`;
- `Accessible Vertical Service Zone`.

These are architectural names and cross-references, not program tokens. Their Markdown source syntax currently causes them to inherit the working mono role, but that implementation accident is not a reason to preserve monospacing in the finished book.

### Decision

**TYP-05A does not admit a publication mono family.**

TYP-05B should typeset the two sequence blocks using the existing Source system and should treat canonical pattern-name references as semantic book references rather than simulated code.

A mono family may be reconsidered only if later corpus work introduces genuine reader-facing code, machine output, fixed-column data or another condition whose meaning materially depends on monospacing. The software nature of the repository is not evidence.

## 6. Mathematical typography is also not earned

The corpus contains **no display-math markers**.

There are 50 bounded symbolic occurrences using characters such as multiplication signs, arrows and inequality/approximation symbols. Typical examples are architectural relations and decision expressions rather than formal equations.

TYP-05 therefore needs to prove that the frozen Source families reproduce the required symbols cleanly and that numeric/unit strings remain legible. It does **not** need a mathematics face, equation layout system or special display-math hierarchy.

## 7. URLs and sources are a real line-breaking problem

The scanner finds **44 bare URLs**:

- **28** in the Part I composite;
- **16** in Appendix E, Sources and Further Reading.

The principal stress is not branding a URL as technical; it is preventing long DOI, journal and web addresses from causing overflow, rag damage or visual noise.

The current working theme uses `overflow-wrap: anywhere`. TYP-05B should test a restrained printed-source treatment and should prefer bibliographic hierarchy and controlled breaking over conspicuous mono styling.

A bare URL does not earn a third type family.

## 8. Lists are extensive but not exceptional typography

The corpus contains **970** list items. Highest current densities include:

- Part V: **137**;
- Part II: **134**;
- Research Agenda: **64**;
- Ground-Supported Façade Access: **40**;
- Part IV: **32**;
- Sources and Further Reading: **30**.

This matters because mixed-content proof must include sustained list rhythm. It does not justify a special technical list voice. Pattern forces, requirements, failure modes and research questions should remain recognisably part of the same book.

TYP-05B should therefore include one list-dense representative page and should first attempt to solve it using the frozen body and section hierarchy plus ordinary list geometry.

## 9. Captions and plate furniture are genuine small-type roles

The controlled publication contains:

- **5** inline figure captions;
- longest inline caption: **484 characters**;
- **17** architectural plate views;
- longest plate caption: **120 characters**;
- plate scales including **1:50, 1:100, 1:200 and NTS**.

The working theme currently gives authored inline captions a sans **8.3 pt / 1.35** treatment. `publication/plates.ts` currently hard-codes Arial for plate titles, scales and captions; that is a known working implementation, not final authority.

These roles must be tested with the exact Source Sans 3 family. TYP-05 may establish the publication treatment for captions and plate furniture as book objects. TYP-06 and PLT retain authority over the final publication-sans/drawing interface and drawing-specific annotation sizes inside architectural drawings.

The boundary is deliberate: a plate caption belongs to book typography; a room label inside the drawing belongs to PLT's drawing contract.

## 10. Numerals, units and ranges

Numeric material is concentrated rather than ubiquitous. Appendix C is the strongest current stress, with Part IV and the plate system adding dimensions and scales outside the bounded unit count.

The default posture for TYP-05B is:

- do not create a separate numeric face;
- use the serif/sans role already appropriate to the surrounding content;
- test tabular figures only where column alignment materially benefits from them;
- preserve proper multiplication signs and unit symbols;
- prevent number/unit pairs from breaking awkwardly where composition permits;
- test architectural scale strings such as `1:100` and `NTS` in small Source Sans 3.

TYP-06 will inherit any proven Source Sans numeral requirements relevant to drawings.

## 11. Smallest coherent role set to test

TYP-05A does **not** freeze final metrics. It authorises the following minimal role model for TYP-05B proof:

1. **compact table** — structured comparison where cells remain relatively concise;
2. **dense schedule** — prose-heavy tabular/schedule information that may need a distinct composition from a compact table;
3. **sequence block** — ordered architectural text/arrow sequence using the existing Source families, not mono by default;
4. **source / URL treatment** — restrained breaking and bibliographic hierarchy without a third family;
5. **caption** — inline figure caption in Source Sans 3;
6. **plate furniture** — title, scale and caption in Source Sans 3, remaining distinct from drawing-internal labels;
7. **ordinary dense list** — control case proving that technical subject matter alone does not earn a new style.

No additional family is authorised.

## 13. What TYP-05B is allowed to change

The next packet may tune only the smallest technical roles needed to make the cases above readable and coherent.

It must not:

- reopen body size, leading, measure or paragraph rhythm;
- reopen TYP-04 hierarchy metrics;
- introduce a mono family without a newly demonstrated reader-facing need;
- make every technical page sans-serif;
- turn tables into dashboard cards or shaded report graphics;
- establish drawing-internal annotation sizes;
- modify production `publication/theme.css` before the wider TYP integration gate.

If Appendix C cannot be made credible as a conventional five-column table at the target physical territory, that is evidence to change the **presentation of the schedule**, not permission to drive type below a comfortable reading threshold merely to preserve Markdown table syntax.

## 14. TYP-05A conclusion

The technical typography problem is smaller and sharper than the repository initially suggests.

The book does not presently need a software-documentation voice, a mathematics system or a family of pattern-specific styles. Its genuine difficult-content problems are concentrated in:

- table/schedule composition;
- long sources and URLs;
- captions and plate furniture;
- numeric/unit behaviour at small sizes;
- two textual sequence diagrams;
- sustained list rhythm.

The frozen Source Serif 4 + Source Sans 3 system remains the complete family architecture entering TYP-05B.
